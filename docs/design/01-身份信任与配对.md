# 01 身份、信任与配对

> 源码:`crates/localtrans-core/src/identity.rs`(473 行)、`pairing.rs`(126 行)、`session.rs` 配对段(L1394-1954)。

## 1. 设计目标

- 每台设备首启自动生成长期身份(Ed25519 密钥 + 自签证书),**无需账号体系**。
- 指纹 = 证书哈希,是设备的全局唯一标识,所有信任/权限/会话都以指纹为键。
- 配对 = 双向人工确认的信任建立仪式:**6 位数字码,只在被连接方屏幕显示**,发起方人工读码输入,防止局域网内冒名设备。
- 权限模型:配对后按 `(browse, download, push)` 三维授权,移除信任即全拒(fail-closed)。

## 2. 身份体系

### 2.1 密钥与证书

`Identity::load_or_create(dir)` 三分支(identity.rs L230-293):

| 分支 | 行为 |
|---|---|
| identity.key + cert.der 都在 | 直接加载 |
| 仅 key 在 | 用该 key 重签证书(**固定序列号 [1]**,保证重签 DER 字节级一致 → 指纹不变),原子写回 cert.der |
| 都缺 | `SigningKey::generate(OsRng)` 全新生成;key 先写、cert 后写(均原子写) |

- 密钥格式:Ed25519 PKCS#8 DER,存 `data/identity.key`。
- 证书:rcgen 自签,SAN CN = "LocalTrans",存 `data/cert.der`。
- `Identity` 结构(L172):`signing: SigningKey`、`cert: CertificateDer`、`pkcs8: Vec<u8>`。

### 2.2 指纹与短码

- **指纹** `Fingerprint = [u8;32]` = `SHA-256(cert.der)`(L178-180)。32 字节,持久化为 64 字符小写 hex。
- **短码** `short_code` = `XXXX-XXXX`(指纹前 4 字节 hex 大写,9 字符,L305-312),供人肉核对设备身份。
- **占有证明**(S2,L206-224):`verify_possession(declared_fp, cert_der, msg, sig)` —— 声明指纹 == SHA256(证书) 且证书内公钥可验 sign(msg)。用于中继注册(见 06 篇)。不做证书链校验(自签 + 指纹绑定已足够)。

### 2.3 信任表(TrustStore)

持久化 `data/trusted_peers.json`,pretty JSON + 原子写:

```rust
TrustedPeer {
    fingerprint: [u8;32],   // serde: 64 hex 字符串
    name: String,           // 对端广播名(自动跟随对方改名)
    alias: String,          // 本地别名,空=未设置(serde default,旧文件兼容)
    paired_at: u64,         // Unix 秒
    perms: Perms,
}
Perms {
    browse: bool,           // 允许浏览共享区
    download: bool,         // 允许拉取文件
    push: PushPolicy,       // ask / auto / deny
}
```

- `Perms::default()`(配对初始授权)= `{browse: true, download: true, push: Ask}`。
- `Perms::denied()` = `{false, false, Deny}`,**信任表查不到记录时的唯一回退**(fail-closed,S5:移除信任即时生效)。
- API:`load`(损坏→warn+空表)/ `save` / `is_trusted` / `upsert` / `remove` / `get` / `all_peers` / `set_perms` / `set_alias`。

## 3. 配对流程(v0.4.0 同意门模型)

### 3.1 设计原则

- **码只在被连接方(B)屏幕显示**。发起方(A)界面永不出现明文码 —— 对称 SAS 方案(v0.4.0 前)因此废弃。
- 码**随连接即焚**:一次配对会话一个码,连接断开码作废。
- 验证为真 = 配对成功的最高事实:**信任写入不依赖任何会话状态**(BUG03 修复,见 3.4)。

### 3.2 状态机与消息时序

```
A(发起方)                                  B(被连接方)
  │ QUIC 连接 + Hello ──────────────────────▶│
  │                                          │ 弹"同意门"(PairingConsentNeeded)
  │                                          │ 60s 超时自动拒绝(consent_timeout_secs)
  │                                          │ B 点「同意」→ 随机生成 6 位码
  │◀──────────────────── ConsentGrant{name} │ 码只在 B 屏显示(PairingCodeShown)
  │ 进入输码界面(PairingCodeEntry)           │
  │ PairCodeSubmit{code} ──────────────────▶│ 常时比对(subtle::ConstantTimeEq)
  │◀──────────────────── PairResult{ok} ────│ Matched: ok=true,随后本地写信任
  │ 收 ok=true → 本地写信任                   │
  │ 双方 SessionUp,配对完成                   │
```

分支处理:

| 情形 | 行为 |
|---|---|
| B 同意前码先到 | 暂存 pending_code,B 同意后立即判定(session.rs L1478-1482) |
| 码错(1-2 次) | 回 `PairResult{ok:false}`,连接保持,A 可重输 |
| 3 次码错 | `FailedOut`:回 ok:false + 记冷却 + 断连 |
| B 拒绝/取消 | ConsentDeny / ConsentCancel → A 侧 PairingResult 失败 + 断连 |
| 同意门 60s 超时 | B 侧关连接 + PairingResult"同意超时"(不记冷却) |
| A 等待中断连 | A 侧补发 PairingResult"连接已断开"(若未收到终止性结果) |

### 3.3 配对码与防暴力

- 生成:`rand::thread_rng().gen_range(0..1_000_000)`,6 位十进制 `{:06}` 零填充(pairing.rs L22-26)。
- B 侧只存 `SHA-256(code)` 哈希;比对用常时相等(防时序侧信道)。
- `PairingMachine`(仅 B 侧):`code_hash / submitted_ok / fails: u8`;`failed_out()` = fails ≥ 3。
- **冷却**:3 次错码 → `record_cooldown(peer_fp)`,`COOLDOWN_SECS = 300`(5 分钟)内该指纹的新连接直接拒绝(session.rs L1946-1953);冷却表顺手清过期项防膨胀。

### 3.4 信任写入(complete_pairing_core,session.rs L1892-1935)

```rust
async fn complete_pairing_core(peer_fp) -> Option<String> {
    if trust.is_trusted(peer_fp) { return None; }        // 幂等,仅首次生效
    let peer_name = match sessions.get_mut(peer_fp) {
        Some(s) => { s.pairing.take(); s.peer_name },     // 正常路径
        None => {                                          // 会话条目丢失(BUG03 兜底)
            warn!("配对完成时会话条目已丢失,兜底写信任");
            format!("device-{}", hex(fp[..4]))             // 指纹前4字节命名
        }
    };
    trust.upsert(TrustedPeer{ name: peer_name, paired_at: now, perms: Perms::default() });
    trust.save();
    Some(peer_name)  // → 发 SessionUp
}
```

**要点**:码验证通过后,即使会话表条目被并发清掉(中继会话死亡/连接抖动),信任也必须写入 —— 否则形成"单向信任"(对端写了我没写,推送/浏览被 Perms::denied() 拒绝,表现如"未配对")。

### 3.5 权限检查点

所有入站请求在 RPC 路由器统一取权限(engine.rs):

```rust
let perms = trust.lock().await.get(&fingerprint)
    .map(|p| p.perms.clone())
    .unwrap_or_else(Perms::denied);   // fail-closed
```

| 消息 | 检查 | 未授权行为 |
|---|---|---|
| SharesReq / ListReq | browse | 回**空列表**(不报错,防探测) |
| MetaReq / FetchReq | download | 静默丢弃(请求方走超时) |
| OfferReq | push 策略 | deny→回拒;ask→弹确认;auto→直接接受 |
| ShareRename/Delete/Mkdir | browse | 回 ShareOpResult{ok:false, "无操作权限"} |

## 3a. 配对生命周期全情况矩阵(2026-08-30 定案,未实现)

来源:specs/2026-08-30-device-identity-network-design.md §7a。

### 3a.1 配对成功 → 自动连接

- PairResult ok 双方收尾后,**主动方立即发起业务会话**(被连方 accept 既有通道复用)——配对成功即"已连接",无需再点一次"浏览"。
- 与连接记忆制衔接:这次自动连接视同"用户主动连接过"(配对是用户点的),此后断网自动重连适用(见 03 篇)。
- 失败兜底:自动连接失败(网络抖动)不报错,停留"在线·已配对",用户手动点浏览即恢复。

### 3a.2 单边移除信任 → TrustBroken 通知(新协议消息)

现状缺陷:A 移除 B 后 B 完全不知情(协议无信任撤销消息),B 卡片仍"已配对";B 下次连 A 走陌生人流程,体验为"我明明配过对,又让我输码?"。

- **即时通知**:A 移除时若会话还在,先发 `TrustBroken { reason }` 再断开(复用加密控制流,不新增明文面)。
- **握手兜底**:A 移除时会话已断(离线移除)→ B 下次连 A,A 在 Hello 阶段发现"B 认为我可信但我已不信任 B"→ 回 TrustBroken 并断开。
- B 收到 TrustBroken:清信任表 + 卡片即时变"待配对" + toast"对方已移除对你的信任"。
- 幂等:双方同时移除(竞态)时 TrustBroken 可能互发,收到时已删则忽略。
- 中继场景:名册互见不受影响(信任与发现是两层),B 仍能看到 A 在线,连接会被 TrustBroken 拒。

### 3a.3 重新配对流程(双盲对称)

任何一边删了信任,重新发起连接时**双方都走完整同意门+配对码**(信任表还留着的一方也走):

| 情形 | 流程 |
|---|---|
| 双方都删 | 纯陌生人,标准流程(现状已对) |
| A 删 B 留,A 连 B | A 走陌生人流程;B 侧也走同意门,文案"设备「X」请求重新配对(曾配对过)" |
| B 留 A 删,B 连 A | 同上对称 |
| TrustBroken 到达后 | 双方都清 → 回纯陌生人流程 |

心智模型:重新配对 = 双方都重新确认,对称无特例。**不留方直接放行**——否则"删方不知情、留方无感放行"会造成幽灵配对假象。

### 3a.4 其他配对情况(现状已对,查漏确认)

- 配对中途取消/超时/拒绝:双方回滚,无残留。
- 配对码 3 错冷却 5 分钟(防暴力)。
- 已配对再发起配对:拒绝"已配对,如需重新配对请先移除信任"。
- 配对成功瞬间对端断网:PairResult ok 已落信任表,断连不影响信任,回"在线·已配对"。

## 4. 交互逻辑(UI 视角)

- **B 侧(PC)**:PairingDialog 同意门(60s 倒计时)→ 同意 → CodeBadge 显示 6 位码 + "结束等待"。
- **A 侧(PC)**:等待界面 → 输码框(仅数字)→ 提交 → 成功/不匹配(可重输)。
- **乐观更新**:B 点同意立即用返回的 own_code 进亮码态,`pairing-code-shown` 事件兜底覆盖。
- 配对成功后 PC 卡片即时刷新(信任表插行 + device-list 重发)。
- Android 侧:同状态机,ConsentRequested/PairingCodeShown/PairingCodeEntry/PairingResult 四事件驱动对话框;输码有超时兜底。

## 5. 安全红线(实现层约束)

1. 明文配对码只存在于:接收方屏幕 + 发起方输入框内存;协议/日志/持久化只有哈希。
2. 指纹在日志中只打前 8 hex。
3. 信任文件损坏 → 重置为空表(不阻断启动,需重新配对)。
4. `Perms::denied()` 是信任缺失的唯一回退,任何"默认允许"都是缺陷。
